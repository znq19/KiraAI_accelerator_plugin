# KiraAI 提速器（kira_accelerator）

**让 KiraAI 反应更快，而且不牺牲质量、不破坏你装的其它插件。**

> 真的能提速吗？如提。她不一定真的有效果，所以我尽量做了一个花里胡哨的前端，希望你看着会有更好的心情享受等待的时刻。
> 一句话：它试图解决的是「为什么 KiraAI 有时候很慢」这个问题。
> 装上之后，你发一条消息，**不用等它把整段话想完才看到第一个字**。

---


## 它治的是什么病

如果你用过 KiraAI，可能有这些感受：

- 🐢 发完消息要**干等十几秒**，屏幕一直没动静，然后突然整段话蹦出来
- 🐢 让它查个东西（要用工具），要等**更久**
- 🐢 有时候它明明能秒答「在的」，却也要想半天
- 🐢 用久了越来越卡

这些**不一定是你的模型慢**，或许能通过一些调用方式改善。

## 装什么、怎么装

1. 下载 `kira_accelerator` 文件夹（或 zip 解压）
2. 放进 KiraAI 的 `data/plugins/` 目录
   ```
   data/plugins/
   └── kira_accelerator/
       ├── main.py
       ├── manifest.json
       ├── schema.json
       ├── icon.png
       ├── wallpapers/          ← 19 张动漫壁纸
       └── web/                 ← 侧边栏面板
   ```
3. 重启 KiraAI（或在 WebUI 里热重载插件）
4. 在插件管理里**启用**
5. 侧边栏会出现「**提速器**」，点进去

> ⚠️ **所有开关默认都是关的。** 这是刻意的——请按下面的「建议开启顺序」一步步来，
> 每开一项都看一眼面板数据。**不要一次全开。**

## 核心功能（按推荐开启顺序）

### ① 观测（默认开，零风险）

记录每一轮的耗时、抢先发送了多少段、思考开没开。
**先开这个跑几天**，看你的实际情况再决定后面的。

两个和「长期运行」有关的细节：

- **计数会随时间长到很大**，所以面板与欣赏模式里的读数会自动用
  `k / M / 亿 / 万亿 / B` 表示（例如 `12.3k`、`1.2亿`），
  数字变长时**字号会自动缩一档**，欣赏模式里读数还会横向扩展占位 ——
  不会撑破面板，也不会把相邻的读数挤变形。
- **计数保留天数**（默认 **30 天**）：计数是持续累计的，
  超过保留期后会在**下次加载/热重载时清零并重新起算**（滚动窗口，不是停止统计）。
  填 **0 = 永久保留、永不清除**。
  判断放在加载时做，不依赖常驻定时器 —— 插件停用期间不执行任何代码，
  下次加载一次性结算，不会因为休眠而漏判。

### ② 强制流式 ⭐ 提速最关键的一项

KiraAI 默认是「等模型把整段话写完，再一次性给你」。
开启后改成「**边写边收**」——不管你的模型提供商本身怎么设置，一律走流式接口。

**效果**：不再有整段空等；首字时间从「整段生成时间」降到「第一句话的时间」。

### ③ 抢先发送 ⭐ 感知提升最明显的一项

配合上面的流式。模型每写完**一个完整的消息段**（一个 `<msg>`），
就**立刻发给你**，而不是攒齐了再发。

**效果**：以前你要等 12 秒才看到全部；现在大约**1 秒就能看到第一句**。

> 这两个是收益最大的。建议先用「生效提供商」填**一个**做灰度测试，
> 确认没问题再全开。

### ④ 自动按需思考（进阶）

简单寒暄不用想（更快更省），复杂问题才开（质量更好）。

**五个信号**（都可配置）：

| 信号 | 权重 | 说明 |
|---|---|---|
| 复杂意图词 | +2.0 | 为什么/怎么/分析/对比/debug… |
| 上一轮工具失败 | +1.5 | 对标 Alife 的「需要处理函数异常」 |
| **上一轮用过工具** | +1.0 | 说明在做多步任务，这轮可能还得继续 |
| **上下文偏离自身基线** | +0.5 | 见下 |
| 用户消息很长 | +0.5 | 信息量大 |
| 简单寒暄 | −3.0 | 直接压到阈值下 |

**★ 上下文信号用「相对自身基线」，不用绝对字符数**

绝对阈值（比如 6000 字符）有个**隐蔽缺陷**：对不同用户意义完全不同 ——
新装用户觉得"很长"，而装了插件的人每轮都 3 万+，于是这个信号**永远为真**。
永远为真 = **零信息量**，而且会**恒定地把你设的阈值往下挪**（阈值 2.0 实际变成 0.5，
你就没法靠调阈值来控制行为了）。

改成和**这个会话自己的基线**比：

```
平时 3.5 万，本轮还是 3.5 万   → 不命中（正常水平）
平时 3.5 万，本轮涨到 5.6 万+  → 命中（1.6×）
之后回落到 4 万以下            → 自动取消（1.15×）
```

- **开阈值 1.6× / 关阈值 1.15×**（两个值**故意不同** = 滞回，避免在临界点反复抖动）
- **基线种子用前 5 轮的「中位数」**（不是第一个样本）—— 中位数天然抗尖峰：
  就算某会话第一轮恰好是个超长上下文（如刚启动读到长历史），
  也不会把基线带跑到那个值上。用首样本作种子的话要十几轮才收敛，
  这期间判定全部失准。
- 基线之后用 EMA 平滑（系数 0.15），**单轮尖峰不会把基线带跑**
- 攒够 5 轮才开始判定；**种子建立的那一轮就能判定**，不用再等一轮
- **基线稳定后才判定**：会话刚起步时上下文从接近 0 涨到稳定值（必然现象，
  不是"异常变长"），这期间基线在追赶，会连续十几轮被判为"偏离基线"。
  所以要求基线**连续 3 轮变化 ≤5%** 后才开始判定 ⇒ 实测爬升期误判从 11 次降到 **0 次**，
  而**真实尖峰照常命中**（这两条都有回归断言守着）。
  一旦稳定就**锁定**，不会因为后面来了个尖峰（基线大幅变化）反而把信号关掉。
- 基线是**每个会话各自独立**的（群 A 和私聊 B 互不影响），
  **插件重载会归零重攒**（状态在内存，调配置属低频操作，不值得为它引入持久化）
- **能上能下** —— 涨了才开，回落就关（这一点和旧实现的关键差别）

**★ 测量包含"本轮刚收到的消息"**

判断发生在 `ON_LLM_REQUEST`，那一刻 `request.messages` 里**只有历史**，
本轮消息还在 `request.user_prompt` 里（框架到 `assemble_prompt` 才合并）。
所以测量时**把 user_prompt 也算进来** ⇒ 量到的就是模型本轮真正看到的上下文
⇒ **本轮即判定，不会滞后一轮**。

（唯一的固有滞后：本轮自己的工具结果撑大上下文 —— 那时判断已经做完了。
工具在第一次 LLM 调用之后才跑，这个无解，也合理。）

**六个厂商风格**（不同家的字段名和取值范围都不同，选错会被忽略或报错）：

| 风格 | 请求体 | 适用 |
|---|---|---|
| `compatible`（默认） | `{"reasoning_effort": "high", "enable_thinking": true}` —— **只用厂商交集值**（不含 `medium`） | 多数兼容网关 |
| `reasoning_effort` | `{"reasoning_effort": "medium"}` | OpenAI o 系列 |
| **`deepseek`** | `{"thinking": {"type": "enabled"}, "reasoning_effort": "high"}`（high 档映射为 **max**） | **DeepSeek V4**（只认 high/max） |
| `enable_thinking` | `{"enable_thinking": true}` | 通义 / 阿里系 |
| `thinking_object` | `{"thinking": {"type": "enabled", "budget_tokens": N}}` | Anthropic / 部分网关 |
| `vllm_chat_template` | `{"chat_template_kwargs": {"enable_thinking": true}}` | vLLM 部署的通义 |

**关思考时也刻意保守**：任何风格都**不发 `reasoning_effort: "none"`**（部分网关 400）。
另**每分钟最多开 N 次**，防被"请认真思考"类话术刷爆 token。

#### 和「提供商里已经开了思考」怎么共存？

这是最容易搞混的地方，直接给结论（都是实测的）：

| 你的情形 | 自动思考开关还管用吗 |
|---|---|
| 提供商是 **OpenAI 兼容系**（阿里 / 硅基 / 火山 / 魔搭 / OpenAI…） | ✅ **管用**。判定要思考 → 我们往 `extra_body` 里补 `reasoning_effort` / `enable_thinking`；判定不要思考 → 默认**不去动**你提供商那边的设置（除非打开下面的「显式关思考」） |
| 提供商是 **DeepSeek** | ✅ **管用**。`thinking` 放 `extra_body`，`reasoning_effort` 放**顶层**（和框架自己的 DeepSeek 客户端写法一致，且只用 high/max 两个合法值） |
| 提供商是 **Anthropic** | ✅ **管用**。`thinking` 放在请求体**顶层**，并且 `budget_tokens` 会自动夹到小于 `max_tokens`（Anthropic 的硬约束，不夹会直接 400） |

**一句话**：插件**不改你的配置文件**，只在每次请求时按判定**临时**补参数；你提供商那边的设置仍然生效，只有当我们判定"这轮要思考"时才会覆盖对应的那几个字段。

> ⚠️ **想让它能"关掉"提供商已开的思考**：把「这轮不要思考时，显式关掉」打开。
> 默认是**关**的 —— 因为不少网关对"关思考"的参数拼写不一致，发错了会 400。
> 打开后插件会按你的「厂商风格」选最保守的写法（例如 DeepSeek 发
> `thinking: {"type": "disabled"}`，Anthropic 则**干脆不发** `thinking` 字段）。

### ⑤ 同轮工具并行（默认关）

同一轮里**多个互相独立的工具**（比如同时读 3 个文件）现在可以**并发执行**，不再一个个等。

**为什么安全性成立**（不依赖"模型很聪明"这个假设）：

> **读操作在数学上可交换** —— 读 3 个文件，任意顺序、任意并发，**结果完全相同**。
> 所以并行它们**不需要模型判断正确**。

反过来，`write_file` / `exec` / `memory_*` 这些**顺序携带语义**（谁先谁后影响结果），
所以必须串行。

**为什么不能指望模型自己排好**：
1. 框架提示词**从没告诉模型工具是串行还是并行**——模型对执行模型是盲的；
2. OpenAI 工具调用协议里**没有表达依赖的字段**——模型只能靠"分不分轮"暗示；
3. 一旦模型以为执行是并行的，它**反而失去排序动机**。

所以模型"批量调用"只是**图省事**，不是**判断过安全性**。

**开关设计**：

| 配置 | 默认 | 说明 |
|---|---|---|
| 启用同轮工具并行 | **关** | 打开才生效 |
| 白名单 | **留空** | **留空 = 全部放行**（只由黑名单控制，不用维护长名单）；填了则只放行名单内 |
| 黑名单 | **已预填 27 条** | 内置默认值**直接写在列表里**，你在这基础上增删即可，不用手抄。（清空 = 没有黑名单，全部放行） |
| 全字匹配 | **关** | 关：关键词命中即可（`exec` 能命中 `manage_background_exec`）；开：必须完全相等 |
| 单批最大并行数 | 8 | 超过就不并行 |

**内置黑名单**（按"已验证的副作用"收录，不靠名字猜）：

- 框架内置：`exec` / `write_file` / `edit_file` / `manage_background_exec` / `memory_add|update|remove` / `session_send`
- 插件：`manage_ignore` / 子代理系列（`spawn|call|stop|resume|collect_subagent*`、`*_subagent_tool`）
- 浏览器插件：`tool_navigate|backend|script|interact|cookie|file|wait|tabs`

> ⚠️ `manage_background_exec` 是**反例教训**：名字看着像只读查询，实际 `action=stop` 会真停任务。
> **不能按名字判定只读。**

**保守规则**：只要有一个工具被判为不安全 ⇒ **整批退回串行**（最坏情况就是没加速）。

**安全性验证**：写了专门的**行为等价性测试** —— 用"逐行照抄框架实现"的串行版和我们的并行版
跑同一批调用，比对 `resp.tool_results`：

```
5 种场景（乱序返回 / 工具抛异常 / 工具不存在 / 超限截断 / 参数非法）
  ⇒ 并行与串行的结果【逐字节相同】
时间：3 × 120ms 串行 362ms → 并行 122ms（3 倍）
```

**只并行"执行"这一段**，其余全部保持串行且按序：超限告警条目、`ON_TOOL_RESULT` 钩子
（插件会在这里 `event.stop()`，框架会因此提前返回）、`assemble_result()`、
`resp.tool_results` 的写入顺序。**可观测行为与串行版完全一致，区别只是等待时间。**

### ⑥ 底层接管（进阶）

| 选项 | 作用 | 风险 |
|---|---|---|
| 复用 HTTP 客户端 | 不再每个步骤都重新建连接池 | 极低 |

> **关于「发送间隔」**：抢发时段与段之间**遵守框架自己的间隔**
> （`bot_config.min_message_delay` / `max_message_delay`），插件**不自造第二个数字**。
>
> 与框架的唯一差别是**等待的时机点**，**等待时长完全相同**：
>
> | | 什么时候等 | 等多久 |
> |---|---|---|
> | 框架 | 发完第 K 段**之后** | `uniform(min, max)` |
> | 我们 | 第 K+1 段就绪、准备发**之前** | `max(0, 目标间隔 − 距上次发送的实际耗时)` |
>
> **两者数学等价**：第 K+1 段在间隔内就绪 ⇒ 都等到满间隔；它来得比间隔晚 ⇒ 都立刻发。
> 实测（3 段、每段生成 2s、间隔 3s）：
>
> ```
>            第1段   第2段   第3段    总用时
> 框架         6.0     9.0    12.0     12.0s
> 抢先         2.0     5.0     8.0      8.0s
>
> 段间隔：框架 [3.0, 3.0]   抢先 [3.0, 3.0]   ← 完全一致，没有绕过
> ```
>
> **真正的差别只在第一段的时机**：框架要等**全部**生成完才发第一段，
> 我们第一段生成好就发 —— 于是后续各段的绝对时刻一起前移。
> 间隔配 `0` 则完全不等。
>

## 安全性：它不会搞坏你的 KiraAI

这是设计时最优先考虑的事。

### 三条铁律

| 铁律 | 意思 |
|---|---|
| **幂等** | 插件重载时不会重复叠加自己的改动 |
| **精确还原** | 卸载时只还原「确实是自己装的」那些改动，**别人改过的不碰** |
| **熔断 + 自动恢复** | 某个接管点连续出错 3 次就临时停用它；**冷却 30 秒后自动试探恢复**；失败则冷却时间翻倍（最长 10 分钟一次）。**任何时候都能在面板点「立即重置」** |

> 熔断**不是永久关闭**。它是「先让它歇一会，再自己试试能不能恢复」。
> 一次网络抖动不该让功能永久失效。

### 出问题会怎样

- 任何一个优化项出异常 ⇒ **立刻回落到 KiraAI 原本的实现**，对话照常
- 面板上「底层接管点健康度」会显示每个点的状态：`生效` / `熔断中 · Ns 后试探` / `未启用`

### 与其它插件的兼容

我们用**真实源码**测过插件市场上 **9 个**较活跃的插件（版本逐一比对，均为最新）：

| 插件 | 我们做的避让 |
|---|---|
| Sustained Chat 可持续聊天 | 它用 HIGH 优先级，我们用 **SYS_LOW**（最低）⇒ 永远最后执行，不抢 |
| Default Chat（z） | 同上 |
| Midflight 随时插话 | 它读 `tool_result.text`，我们**只读不改** |
| KSM 会话合并与互通 | 它订阅 `ON_MESSAGE_SENT` ⇒ 我们抢先发送时**补广播**这个事件 |
| Anti Harass 防骚扰 | 同上 |
| Model Fallback | 它读 `client.model.*` ⇒ 我们的代理层**原样透传** |
| SubAgent | 它会**并发**用同一个客户端 ⇒ 我们的递归护栏用 task-local，不误判 |
| **QQ 增强**（xxynet/kira-ai-plugin-qq-enhance） | 它的「**表情独立成行**」挂在 `AFTER_XML_PARSE` 钩子上 ⇒ 我们抢先发送时**补广播这个钩子**，并**按钩子改写后的内容发送**（不补就功能失效） |
| **XML 结构修复器**（znq19/xml_tag_fixer） | 它会**改写 `text_response`**（补 `<msg>`、空行分段拆条、跨消息合并、转义实体）⇒ 我们把"剥离已抢发段"从**按序号**改成**按内容匹配**，文本被改写也切得准 |
| Builtin kira-ai（XML 校验） | 它在 `ON_LLM_RESPONSE` 里按**完整原文**做校验 ⇒ 我们**不改写** `text_response`，只打私有标记 |

## 常见问题

**Q：装了就一定会变快吗？**
A：流式相关的一定有效果。但**具体快多少取决于你的模型和网络**。
先开「观测」跑一段时间，面板上的「首段发出耗时」会告诉你实际情况。

### v1.0.11

**★★★ 墨染"看不出效果 / 硬切"—— 三个叠加的原因**

| # | 问题 | 说明 |
|---|---|---|
| ① | **SVG 尺寸解析成 0×0** | 载体用 `width:100%;height:100%`，在 `.wallpaper` 容器内实测为 0×0；而内部 `<image width="100%">` 是**相对该 SVG** 解析的 ⇒ 整张画不出来 ⇒ 收尾时新图突然出现 = 硬切。改用 `100vw/100vh`。 |
| ② | **mask 单位不匹配** | `maskUnits="objectBoundingBox"` 却把内部 `<rect width="100%">` 写成 userSpaceOnUse 的单位 ⇒ 遮罩行为不可预期。改为 `userSpaceOnUse`。 |
| ③ | **铺不满 + 扩散被压缩** | 终点 `BIAS1=0.30` 时实测**只能覆盖 70%** ⇒ 剩下 30% 靠新图兜底 = 硬切。但**单纯调大终值又会把中段也推满**（该阈值函数在阈附近极陡）⇒ 改用**幂曲线 `p^2.5`** 让 bias 前半段保持低位、后半段才越过阈值。 |

最终覆盖率曲线（实测）：`10%=0%  30%=2%  50%=32%  70%=99%  100%=100%`
—— 真正"慢慢渗开、最后吃满"，且终点**确实铺满**（`BIAS1=1.35`）。

**★★★ 燃纸"燃完出现旧图帧"**

收尾写的是"先设 `opacity=0`，再用 `[{opacity:1},{opacity:0}]` 起动画"——
**动画的首帧是 1**，会把刚设好的 0 **拉回 1** ⇒ 旧图闪现一帧。
改为从当前值（0）开始。

**★★ 收尾顺序（旧图闪现的另一个来源）**

`wpSettle` 原来先 `wpNormalize(fromId)` 后 `remove("on")`。而 `wpNormalize`
会清空 inline `opacity` ⇒ 在"清空"到"摘 `.on`"之间，CSS `.wp-stage.on .wp-img`
仍让它可见 ⇒ **旧图闪现**。改为**先摘旧层 `.on`、再归一化**；
新层则**先加 `.on`、再归一化**（避免反向的瞬间空窗）。

**判据新增**（都是**实测校准**，不是估计）：SVG 视口单位、mask 单位、
覆盖率（起点 0% / 终点 100%）、曲线形状（中段必须在扩散）、

**★★★ 修掉我上一版引入的 bug —— 它让重复发送"更明显了"**

1.0.8 里我加了「台账只消费一次」的标记，清理挂在 `@on.final_result` 上。
但有两个问题叠在一起：

1. **我用了 `Priority.SYS_LOW`** —— 框架源码里明确写着

|---|---|

### v1.0.8

**★★★ 重复发送：多步 agent loop 下整批重复（用户截图：同一批消息出现两遍）**

框架的循环形状（`message_manager.py:793`）：

```python
async for step in agent_executor.run(agent_ctx, max_steps=max_steps):
    if not await send_llm_text(llm_resp):   # ← **每一步**都调 send_xml_messages
        break
```

也就是说 `send_xml_messages` 在一轮里会被**调用多次**（每步一次）。而台账原来在它的
`finally` 里就被 `pop` 掉 ⇒ **第二步时台账已空 ⇒ n=0 ⇒ 不剥离 ⇒ 该步文本整段重发**。

修法是两个方向**同时**收住的（只做一边都会出问题）：

| 做法 | 后果 |
|---|---|
| 只"消费完就清"（旧） | 多步第二次数不到 ⇒ **整批重复** |
| 只"留到轮结束"（过头） | 第二步拿台账**按序号切** ⇒ **误切 = 丢内容** |
| ✅ 留到轮结束 **+ 只消费一次** | 既不重复、也不丢内容 |

所以台账现在：**活到轮结束**（由 `final_result` 统一清），但加一个
`_ledger_consumed` 标记 —— **只有第一次调用会消费它**，后续步 `n=0` 原样交给框架
（后续步的文本本来就该发，从没抢发过）。

新增 `tests/test_dup_send_multistep.py` 专门盯这个场景。

**★★ 与 xml_tag_fixer 的兼容性实测（拉取真插件跑）**

`xml_tag_fixer` 在 `@on.llm_response(priority=HIGH)` **重写 `resp.text_response`**
（补标签 / 拆消息块 / 实体转义 / 反斜杠还原），而我们的剥离是**按内容比对**的。

实测结论：**兼容，四种改写后都能剥干净**。它只改 `text_response`，
**不重建响应、不碰 `__dict__`**，所以我们的标记不会被它破坏。
新增 `tests/test_compat_xmlfixer.py`（设 `XFIX=/path/to/main.py` 即跑）把这条锁住。

## 给维护者：改前端时必读（两个 API 前缀）

KiraAI 的插件端点分两类，**前缀不同**，写错就是 404：

| 端点类型 | 前缀 | 例子 | 来源 |
|---|---|---|---|
| **框架自带** | `/api/plugins/<id>/…`（**复数 s**） | `config` / `icon` / `reload` / `readme` | `webui/routes/plugins.py` |
| **插件自己注册** | `/api/plugin/<id>/…`（**单数**） | `health` / `wallpapers` / `breaker/reset` | `@register.api` → `core/plugin/plugin_registry.py:1096` |

面板里因此有**两个常量**（`web/index.html`）：

```js
const API  = "/api/plugins/" + encodeURIComponent(PLUGIN_ID);  // 框架端点
const PAPI = "/api/plugin/"  + encodeURIComponent(PLUGIN_ID);  // 插件自定义端点
```

**加新端点时**：先想清楚是框架的还是自己的，再用对应的常量。

### 这个坑真的踩过（2026-09-23，用户实测）
现象：面板右上角**「未连接」** + 壁纸**一张都没有**（选择器显示「全部 0 张」）。

根因：前端对**两类端点都用了复数** ⇒ 插件自定义端点全部 404。
- `/health` 404 ⇒ 轮询失败 ⇒ 显示「未连接」
- `/wallpapers` 404 ⇒ 列表为空 ⇒ 没有背景图
- 而 `/config`（复数）**恰好是对的** ⇒ 配置照常显示，**所以症状看起来像"两个不相关的 bug"**

### 为什么以前没发现（方法论教训）
当时验证面板用的是「**注入假数据**」→ 只能证明 HTML/CSS 没问题，
**证明不了 URL 真的能通**。现在补了两道真检查：

1. `tests/test_frontend_api.py` —— 纯静态比对：前端拼的 URL ↔ `@register.api` 真实声明，
   并带**反向验证**（把前缀篡改成错的必须报红）
2. `tests/test_real_api.py` —— **真导入框架 + 真实例 + 真 FastAPI + 真 HTTP 请求**，
   逐个端点断言不 404；还会从 `index.html` 里抽出所有 URL 逐个真请求
   （框架源码随插件固定一份在 `../kira_fw_v2346/`，见其 README）
